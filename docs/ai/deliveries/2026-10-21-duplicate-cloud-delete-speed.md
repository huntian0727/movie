## 原因

旧确认删除流程：页面 `preflightManualDelete` 对虚拟挂载执行 stat，后台 `previewDuplicateResolveSafely` 又对同样文件执行 stat。主进程再远端强制刷新整批，之后 **对每个待删文件重复刷新一次保留项和待删项**，才单独调用远端删除；同目录文件重复执行 `GetMountPoints`、`GetSubFiles`，网络/网盘响应慢时放大等待。

## 修复

1. 在调用新的受控删除主进程 API 时，页面跳过冗余的、可能阻塞虚拟挂载的旧 `preflightManualDelete`；后端仍执行独立验证，旧普通删除回调的前置复查保持不变。
2. 后端区分本地普通文件与 CloudDrive：本地维持原受管隔离/原子恢复保护和完整预检；CloudDrive 不依赖虚拟挂载的 `realpath` 或逐文件 `stat` 作为可信真相，而使用强制远端目录刷新核对 providerId/providerPath/大小/修改时间及同组保留者。
3. 主进程先完成整批安全校验，再每三个 CloudDrive 候选组成一个波次。一次 `refresh` 同时验证这些候选及保留者，然后最多三个单对象 `delete` 并行发出，绝不使用旧禁用的快速通道，也不对多对象发送无法归因的单条删除操作。
4. 等待同批所有结果：成功数逐个入账，永久删除释放空间与转入回收站区分；任一远端通信断连或数据库确认失败则标记未知，并停止后续波次，未知项不自动重试；API 返回失败时强制再查该文件，只有同一远端对象仍存在才作为明确失败，否则视为未知。
5. 入口保留每组选择的 keepVideoId；普通资料库永久删除守卫、旧快速通道、任务占用/连接绑定校验仍保持。
6. `scripts/package-development.mjs` 增加环境变量 `MOVIE_SAFE_STAGE_LOCAL=1` 时输出到 `release/local-optimized/win-unpacked`，避免覆盖当前运行中的日常可执行文件；不产生安装器和公开发布。

- 模拟 API 返回失败：确认原文件仍存在才算明确失败，若远端已缺失则作为未知、不自动重试。

- 没有调用真实 CloudDrive 远端删除 API，也没有删除任何用户真实媒体。模拟的 8 -> 4 请求减少并不代表实际网络已测得相同的耗时比例。仍需用户在不重要的测试副本上验收。
