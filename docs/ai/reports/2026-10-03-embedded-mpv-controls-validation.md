# 内嵌 MPV：连续控制与等待状态验证

## 当前结论

本轮仅修改隔离原型及测试，没有对接正式播放器。连续跳转合并、媒体变化操作串行、切换/退出清理具有可行性；云盘等待没有消除。实际快捷键仍未通过，因此不建议现在默认替换正式播放器。此前“播放推进通过不等于持续无缓冲”的限制仍有效。

基线 `073dcca3e09612251b5f5581e3e4a8c257e9205e`；分支 `ai/embedded-mpv-controls-validation`。沿用已固定的 Electron 33.4.11、libmpv、C# 宿主及匿名样本，不重新下载 DLL，不更改原文件。详细运行时来源见 [首轮验证](2026-10-03-embedded-mpv-spike.md)；先前证据见 [seek 验证](2026-10-03-embedded-mpv-seek-validation.md)。

## 控制策略与边界

通过 `--spike-controls=1` 开启候选实现：

```text
界面 seek/rotate → 一个执行中操作 + 每种一个最新待执行值
                   ↓ native ack + token/属性 + seeking=no + 新增 restart
                 完成后执行下一项
加载另一个 token / 关闭 → 清空旧队列
30s 超时 / native 拒绝 → 清空队列，显示操作未完成
```

五次突发跳转到 2/4/6/8/10 秒应实际只发送 2 和 10；中间请求合并，不中断已经开始的原生读操作。混合序列 seek 3 → rotate 90/180/270 → seek 9，应发送 seek 3、rotate 270、seek 9，最终属性必须匹配。每种待执行项上限一个；同一种合并不改变其既有队列位置，不承诺严格按最后一条输入的时间排序。

检查通过仅代表请求提交、重启和最终状态满足条件，不代表连续画面/声音真实输出验收。突发请求同步发出，不是实际鼠标拖动性能测试。失败/超时清理用单元测试模拟，不是断网或拔盘实测。

## 已执行的真实媒体结果

第一批使用四个本地 12 秒中性合成样本：

| 媒体 | 五次请求合并到目标 ms | 混合控制 ms | seek 中关闭 ms | 结果 |
|---|---:|---:|---:|---|
| H.264/AAC MP4 | 310 | 621 | 181 | PASS |
| HEVC/AAC MP4 | 373 | 622 | 168 | PASS |
| HEVC/DTS MKV | 313 | 621 | 157 | PASS |
| VP9/Opus MKV | 312 | 626 | 162 | PASS |

全部实际发送 `[2,10]`，混合发送三项，进度推进、重新加载取消旧操作、seek 期间关闭宿主通过，待执行项清零。整轮 main / renderer 100ms 心跳最大额外延迟 18.39 / 16.20ms，renderer 181 次心跳；实际 DOM 文本阶段 reading 45、seeking 2 次采样。

第一批真实挂载盘样本为同一匿名 27.698 秒 4K HEVC/AAC 短片（261,428,404 bytes），结果：

- 五次请求合并到目标：15,396ms；只发送 2、10 秒。每项实际完成等待约 1.523s、13.812s。
- 跳转/旋转混合：22,503ms；实际只发送 seek 3、rotate 270、seek 9，均完成。
- 继续播放 PASS，重新加载后旧的 7 秒待执行请求没有泄漏；seek 期间关闭约 1,146ms，宿主退出码 0，队列清零。
- main / renderer 最大心跳额外延迟 21.30 / 11.20ms，renderer 540 次；DOM 显示阶段 reading 382、buffering 32 次。它说明读取期间 JS 和状态文本仍在更新，不是严格点击延迟或主观“零卡顿”的证明。

这些耗时来自不同序列、两个真实跳转及缓存状态，不能直接和上一轮单次 seek 比较，也不能称为网络提速。没有清空 CloudDrive 缓存、没有复制完整本地对照、没有测量网络读量，无法确定唯一瓶颈。

为防止恢复旋转失败被漏判，第一批完成后又增加了“恢复到 0°必须 ready 且属性为 0”的判据；最终源码的补跑结果见交付记录。第一批结果独立保留，不覆盖为最终补跑值。

最终源码补跑：四个本地格式及同一个云盘样本均 PASS。云盘两次跳转合并耗时 17,811ms、混合控制 26,657ms、seek 中关闭 240ms；仍实际只发送 `[2,10]` 和三项混合控制，旧 token 待执行项未泄漏。main / renderer 心跳额外延迟 12.48 / 14.10ms，619 次 DOM 心跳，其中 reading 449、seeking 28、buffering 6。更长的等待进一步说明网络/缓存状态波动，不能宣称调度让读取本身变快。

最终本地四个格式合并耗时分别 296/311/376/311ms，混合 624/624/562/608ms，关闭 178/187/192/177ms；main / renderer 额外延迟 16.85 / 15.70ms。两批每批 5 个媒体控制序列，共 10 个 PASS；它们不是 10 种不同媒体。最终补跑未和全量质量门禁并发执行，未测冷缓存。

原始结果存于本机隔离目录 `lamian-embedded-mpv-spike-20261003` 的 `controls-synthetic.json`、`controls-cloud.json`、`controls-final-synthetic.json`、`controls-final-cloud.json`、`controls-keyboard.json`；不提交私有清单、运行报告或二进制。

## 键盘验证：仍未通过

在中性 HEVC 合成视频暂停状态下，仅操作隔离窗口，使用 computer-use：

- Space（初始、显式激活后）均没有取消暂停；F 没有全屏。
- 点击 HTML 顶栏、显式激活实验窗口后仍未生效；已有实际 native 场景中的 Esc 失败未获得修复证据。
- 实际操作报告只有退出按钮的 quit，没有对应键盘动作；退出按钮有效，宿主正常清理。
- 候选处理限定于实验窗口 webContents 的 `before-input-event`，再由 preload 转发至 UI；没有使用全局快捷键、系统键盘钩子或对其他应用的按键监听。[Electron 官方文档](https://www.electronjs.org/docs/latest/api/web-contents/#event-before-input-event)描述了此事件的作用；实际跨进程原生窗口内能否收到仍须实测。

不能把 UI Automation 的文档焦点描述当作实际 Win32/Chromium 输入路由证明。目前只确认简单 Electron 层候选处理未让真实按键生效，未确定唯一丢失节点。后续需要专门追踪自有 native 子窗口输入路由，或验证另一种画面嵌入方式；不能用全局拦截按键掩盖局部焦点问题。

## 下一步
