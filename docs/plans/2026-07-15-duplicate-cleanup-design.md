# 重复视频识别与批量清理设计

## 背景

当前资料库只保证“同一路径重复扫描不会重复入库”，并不具备“同一内容的多个副本识别与清理”能力。对用户来说，最常见的问题不是单一路径重复，而是同一部影片被拷贝到多个目录、重命名后再次导入，或者长期积累出多份完全相同的文件，占用空间并影响浏览体验。

本次设计聚焦“精确去重”。第一版只识别内容完全一致的重复文件，并提供批量永久删除能力，不尝试把 4K/1080p、不同封装、不同字幕版本等“同一电影不同版本”混在一起处理，避免误删。

## 目标

本次设计围绕四个目标展开：

1. 在不改变现有扫描和浏览主流程的前提下，识别内容完全一致的重复文件。
2. 提供独立的“重复项”视图，让用户在删除前能逐组检查保留项与待删除项。
3. 第一版直接支持批量永久删除磁盘中的重复文件，但保持强确认和最小误删风险。
4. 尽量复用现有 `LibraryShell`、详情弹窗、播放器和文件操作能力，把改动收敛在已有架构内。

## 范围

第一版包含以下能力：

- 扫描后为候选视频计算内容指纹。
- 根据内容指纹生成重复组。
- 侧边栏新增“重复项”视图。
- 每组自动推荐一份保留文件，其他文件默认列为待删除。
- 支持用户逐组改选保留项。
- 支持批量预检查、强确认和批量永久删除。
- 支持显示失败项与失败原因，并允许后续重试失败项。

第一版明确不做：

- 不识别“同一电影不同版本”。
- 不做后台自动删除。
- 不允许整组全删，每组至少保留 1 个文件。
- 不在普通“所有视频”页直接混入去重操作。

## 识别策略

重复识别分三层完成，先快后准。

第一层是粗筛。先按 `sizeBytes + durationMs` 把视频分桶，只对同桶且数量大于 1 的文件继续处理，避免对全库所有文件无差别计算指纹。

第二层是内容指纹。第一版不做整文件全量 hash，而是读取文件头、中间、文件尾的固定片段，再结合 `sizeBytes` 计算一个 `sha256` 指纹。分段指纹能较好地兼顾速度和准确度，足以覆盖“同内容副本”这个目标。

第三层是重复组生成。只有 `contentFingerprint` 完全一致的文件，才会被归入同一重复组。每组至少 2 个文件才展示在“重复项”页面。

## 推荐保留规则

每个重复组默认自动选择一份“推荐保留”文件，排序规则按以下优先级稳定执行：

1. 已收藏优先。
2. 分辨率更高优先。
3. 文件更大优先。
4. 修改时间更新优先。
5. 导入时间更早优先。
6. 路径字典序作为最终兜底。

页面需要向用户显示保留原因，例如“已收藏”“分辨率更高”“文件更新”，避免推荐结果变成黑盒。

## 页面交互

侧边栏新增一个独立入口：`重复项`。该入口不混入“所有视频”“收藏”“最近播放”等现有视图，避免污染主浏览路径。

“重复项”页面分为两部分。顶部是总览区，展示重复组数量、涉及文件总数、待删除文件数、预计释放空间，并提供“按推荐自动选择”和“开始批量清理”按钮。下方是重复组列表，每组显示组标题、推荐保留项、待删除项以及可释放空间。

每个重复文件条目展示这些信息：

- 文件名
- 所在路径
- 分辨率
- 文件大小
- 时长
- 修改时间
- 收藏状态

每组支持这些交互：

- 设为保留
- 播放
- 查看详情
- 打开所在文件夹

一旦用户把某个文件设为保留，同组其他文件自动切换为待删除状态。界面上不提供“整组全删”的路径。

## 批量删除确认流程

批量删除分成两步，避免误触即删。

第一步是预检查弹窗。点击“开始批量清理”后，主进程根据当前选择生成一份预检查摘要，明确展示：

- 共多少组重复
- 将保留多少个文件
- 将删除多少个文件
- 预计释放多少空间

第二步是强确认弹窗。用户需要手动输入 `DELETE`，只有输入正确后，“确认删除”按钮才可点击。这样即使第一版支持批量永久删除，也能把误删风险压到较低水平。

执行过程中，若发现某组没有保留项或某组待删除计划非法，主进程直接拒绝执行，并把错误返回前端。

## 执行与失败处理

正式执行批量清理时，建议采用逐文件处理而不是整批事务硬回滚：

1. 根据用户方案生成删除计划。
2. 再次校验目标文件是否存在。
3. 逐个删除磁盘文件。
4. 删除成功后同步移除资料库记录。
5. 单个文件失败时记录失败原因并继续后续项。

处理完成后返回结果面板，至少包含：

- 成功删除数量
- 失败数量
- 实际释放空间
- 失败文件列表
- 失败原因

失败原因优先覆盖这些场景：文件被占用、权限不足、文件已不存在、路径访问失败。

## 数据与状态设计

第一版建议只给 `videos` 表补最少字段，不额外持久化重复组关系：

- `content_fingerprint TEXT`
- `fingerprint_status TEXT`
- `fingerprint_updated_at TEXT`
- `fingerprint_error TEXT`

其中 `fingerprint_status` 取值为 `pending | ready | failed`。重复组在查询时按 `content_fingerprint` 聚合生成，这样实现更简单，也更贴近现有 repository 的查询方式。

共享类型建议补充：

- `FingerprintStatus`
- `DuplicateCandidate`
- `DuplicateGroup`
- `DuplicateResolvePlan`
- `DuplicateResolvePreview`
- `DuplicateResolveResult`

## 主进程与 IPC

主进程需要补上三类能力：指纹状态维护、重复组查询、批量清理执行。

Repository 层建议新增：

- 标记指纹 `pending / ready / failed`
- 查询重复组
- 生成预检查结果
- 执行清理计划

IPC 层建议新增三个主接口：

- `duplicate:list`
- `duplicate:preview-resolve`
- `duplicate:resolve`

第一版可以不急着补“重试全部失败指纹”或“强制重新计算所有重复项”，后续再加。

## 与现有结构的衔接

该能力建议继续挂在 `LibraryShell` 这条主线里，而不是新开窗口或单独路由。侧边栏增加 `duplicates` 视图后，内容区在普通视频列表和重复组页面之间切换即可。

播放、查看详情、打开所在文件夹、永久删除等能力尽量复用已有组件和主进程文件操作逻辑，避免为了去重再造一套平行链路。

## 风险与回归点

主要风险包括：

- 分段指纹在极少数边界文件上仍可能不如整文件 hash 稳妥。
- 大量候选文件首次补算指纹时，后台任务可能持续较久。
- 批量删除涉及磁盘写操作，最需要关注失败降级和结果反馈。

回归重点包括：

- 新扫描文件和变更文件能进入指纹待计算状态。
- 指纹计算完成后重复组列表能正确更新。
- 推荐保留规则稳定，不会来回漂移。
- 每组至少保留 1 个文件的约束始终成立。
- 预检查摘要、强确认输入和正式执行链路一致。
- 删除成功后资料库、侧边栏计数和页面统计同步刷新。
- 删除失败时不会中断整批，其它文件仍能继续处理。
