# 日常开发、绿色测试与发布文档

约定日期：2026-10-14（北京时间），来自维护者确认。日常开发持续使用最新功能；维护者认为稳定、明确要求准备发版时，才制作候选绿色包并发布。

## 三个阶段

| 阶段 | 用途与数据 | 进入条件 |
| --- | --- | --- |
| 日常开发版 | 维护者真实使用；交付前更新实际桌面程序和快捷方式，不只推源码 | 每项开发完成、检查通过并完成对应桌面验证 |
| 绿色候选包 | 从确定 Commit 构建；使用独立测试库，必要时用关闭后的真实库备份副本验证升级 | 维护者明确要求准备发版 |
| GitHub 正式绿色版 | 对公众提供程序、校验和、源码、许可、版本教程和发行说明 | 具体成品通过必要检查、维护者授权公开 |

源码日常推送 GitHub 是备份与协作，不自动发布 Release。不同本地程序可能尚未同步；以实际快捷方式目标、Commit 和构建证据为准，不凭窗口名或版本号推断相同。当前历史“日常版/隔离绿色测试版”并非自动同步更新，统一交付须按任务实际执行。

## 每次功能迭代做什么

本机日常版使用 `npm run package:development` 重新生成 `release/win-unpacked`，标记为不可分发的 `local-development`，沿用 `local-video-manager` 数据目录。该命令只生成本地目录，不生成安装器、ZIP 或发布附件；媒体运行库仍按原锁文件校验。执行前正常关闭日常程序并保留最近三份旧程序存档，完成后从实际桌面快捷方式验证。公开发布继续使用原有发行门禁。

1. 按 `AGENTS.md` 检查工作区、备份、创建功能分支，保留真实资料库。
2. 完成修改，运行现有适用质量检查，并验证本轮变更的实际桌面入口；默认交付日常开发版。临时只更新隔离版须明确记录维护者的选择。
3. **立即更新根目录 `CHANGELOG.md` 的 `[Unreleased]`。** 写用户能感知的新增、修复或变化；附日期与必要的操作差异，不把源码已合并写成公众已下载到。
4. 同步修改受影响的 `docs/USER_GUIDE.md` 章节，注明尚未发布。没有用户行为变化的维护任务，在交付记录解释“教程无需变更”的原因。
5. 在 `docs/ai/deliveries/` 记开发/桌面/测试事实、文档影响和发布状态。检查通过后使用既有交付脚本同步源码，不自行创建公开版本。

不必每次重写整份教程或再审所有不变组件；修改相关章节并复用已有可靠证据。原生库、数据库、文件操作或打包变化时，补对应专项验证，保留既有安全门槛。

## 同一台电脑的测试安排

- 本机日常版使用真实库，开发前备份。
- 本机隔离候选包验证具体功能、API 与备份副本升级；不让候选包修改正在使用的同一份库。
- Windows 沙盒验证完整解压、首次启动、无开发工具运行、扫描和播放。网盘可由宿主机挂载并只读映射；同机 API 使用本机隔离库测试。
- 单机不能证明其他硬件和全部 Windows 环境均兼容。记录实际系统和未覆盖范围，不把另购电脑或等待其他系统设为通用前置条件。

沙盒启用与账户登录由用户按实际环境完成；不通过关闭防护、跳过证书校验或更换发行身份来消除测试失败。

## 维护者说“准备发布”时

### 先确定本次范围

- 从上一个 Release tag 到候选 Commit 检查差异，将要发布的 Unreleased 条目确定为一个新版本；不要按“main 已有”推断已全部验收。
- 更新真实 `package.json` / lockfile 版本及受影响的精确版本批准、来源/QA 证据，依照 [源码绿色版流程](SOURCE_COMMUNITY_RELEASE.md) 构建。
- 复用未变化的运行库来源、许可和声音验收证据；新应用仍完成 CI、包内容核对和变更相关验收。新运行库或数据库修改补受影响检查。

### 文档与成品一起准备

| 文件 | 发版时的动作 |
| --- | --- |
| `CHANGELOG.md` | 将本次条目归入真实版本与发布日期，保留新的 Unreleased；未进入候选的条目继续留在 Unreleased |
| `docs/USER_GUIDE.md` | 核对候选实际界面与入口，移除本版本已发布功能的“未发布”标记，更新适用范围 |
| `docs/user-guide/<版本>.md` | 从已核对内容形成完整版本快照，不能包含未来功能；修正文档错误时明确标注修订日期 |
| `docs/QUICK_START.md`、`README.md` | 更新下载文件名、版本、默认入口和教程链接，普通用户不被引到开发命令或历史阻塞记录 |
| `docs/releases/<版本>.md` | 写用户变化、更新方法、资料库/凭据影响、实际环境、已测与未覆盖范围；链接对应版本教程 |
| GitHub Release 正文 | 使用本版本说明，链接版本教程、变更记录和必要附件；不可用一份滚动开发教程冒充固定版本说明 |

候选发现问题，先回开发分支修复、更新记录，再生成新候选；通过的**具体最终成品**才可发布。若公开包需要重新构建，必须按现有流程核对差异和必要验收，不能声称新包就是之前测过的字节。

### 发布与最后核对

1. 文件版本、源码 Commit、精确 tag、公开批准、原生来源、校验和及教程一致；不要改名测试包冒充正式包。
2. 新 Release 同时提供对应程序、校验和、应用及原生源码、许可/验证说明，按维护者授权发布。
3. 从发布页确认教程链接可打开，程序下载名正确，SHA-256 匹配；记录 Release URL 和具体范围。
4. 保留旧 Release 的 tag 与程序附件。若只补旧版本教程，可单独补充说明并标明日期，不替换旧二进制、不挪 tag、不把开发功能写进旧版能力。

当前有检查、构建和交付脚本；本约定由后续开发任务执行，**没有新增定时自动发布、应用内自动升级或推送即发版机制**。现有许可、凭据、删除安全和发布审批规则继续适用。
